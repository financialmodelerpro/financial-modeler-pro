Schema-tolerant: on a pre-239 database the accounts read comes back empty and behaviour is exactly pre-239. - **MODULE 10 STEP 8: SEATS ARE ENFORCED (2026-09-03, mig 237 APPLIED). NEW `verify-seats` 42; suite 154 verifiers.** A seat is a DISTINCT PERSON ON AN ACCOUNT, counted across every project it owns, on every platform. **The owner consumes one**, so Pro at 1 seat means a single-person account and collaboration is a Firm feature. Firm is 10. An admin raises a client with an override; extra seats are invoiced manually, outside the platform.
  - **THE COUNT LIVES IN THE REGISTRY LAYER, NOT IN REFM** (`src/shared/admin/seats.ts`), and iterates `PROJECT_SOURCES`. A counter reading `refm_project_members` directly would keep returning a plausible number and start UNDER-counting the day ERM or BVM shipped, which is the worst kind of wrong: quiet, believable, and in the customer's favour until someone audits it. A source with no membership declared is SKIPPED rather than counted as zero members, and a failed read THROWS rather than contributing nothing.
  - **THE OWNER IS COUNTED UNCONDITIONALLY**, whether or not a membership row happens to exist for them. Migration 231 seeded one per project, but a project created through a path that writes no membership would otherwise make the owner free, and "Pro is 1, which means no collaboration" only holds if the owner IS that one. **A soft-deleted project's members do not count** (`deleted_at` makes it unopenable, so charging for that access would bill for nothing); **archived projects DO count**, because archiving is visible, reversible and leaves the project openable.
  - **A ROLE CHANGE IS NOT A NEW SEAT.** The question asked is "does this person already hold a seat anywhere on this account", NOT "will a row be inserted". The write is an UPSERT, so a demotion travels the same path as an add, and a check counting rows-to-be-written would have refused to demote the tenth member of a full Firm account. Adding an existing collaborator to a SECOND project is free for the same reason, which is what "counted across all projects" means.
  - **ONE ENFORCEMENT POINT, and it is genuinely one.** The upsert in `POST /api/admin/project-members` is the ONLY insert into any membership table in the codebase: create and duplicate seed none, and the other writes update `priority` / `sort_order` on existing rows. The check sits AFTER the user lookup, so a seat is never refused for somebody who does not exist, and BEFORE the upsert, so it blocks rather than warns. A counting failure REFUSES: a seat handed out by an errored read is invisible until an audit.

- **MODULE 10 STEP 7: COMMENTS (2026-09-03, mig 236 APPLIED). NEW `verify-comments` 50; suite 152 verifiers.** People's words about the model, beside the machine's record of it. **A THIRD TABLE, `refm_project_comments`, and both reasons are stated rather than assumed**: `refm_project_changes` (234) is what the SYSTEM observed, appended by the save path and immutable by trigger, whereas a comment is written, edited and withdrawn BY A PERSON; and `refm_project_versions.comment` (153) is the required note on ONE save, with one author, no thread and no resolve state.

  - **REPLIES ARE ONE LEVEL AND THE DATABASE ENFORCES IT.** `trg_refm_comments_one_level` refuses a reply whose parent is itself a reply, and a comment replying to itself.
